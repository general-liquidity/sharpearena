\section{Commands that produce every number}\label{app:commands}

All commands run from the repository root with the \texttt{sharpearena} Python package installed. Each script fixes and serializes its seeds, and the evidence manifest records file hashes and producer commands.

\paragraph{Version provenance.} This is the paper's single provenance statement. F1 serializes \texttt{sharpearena} 0.9.0; several other F1--F8 evidence files do not serialize a runtime version, so this paper does not reconstruct one from their creation dates. Historical review records identify SharpeBench 0.5.0 as the companion scorer used during that evidence cycle, but the empirical JSON does not serialize a SharpeBench version. The present engineering guarantees are verified against the source and tests bound by the manifest; they do not retroactively establish that every current guard was active when the historical empirical tables were generated. F4 and F5 are generated by the documented finite-panel estimator and normalized-flow producers, and the witness artifact serializes its producer and common-random-number configuration. No current-model artifact or trained-policy result is admitted. A superseded convenience-sample forecast pilot is retained as an engineering trace and excluded from every result in this paper.

\paragraph{Content provenance.}
\begin{verbatim}
python paper/src/make-provenance.py
python paper/src/check-provenance.py
\end{verbatim}
The first command writes \texttt{paper/evidence/provenance.json}; the second validates it against the tree.
The manifest records the commit it was generated at, whether the working tree was dirty at that moment, a content hash over the Rust, Python, manifest and producer-source snapshot, and the SHA-256 digest of every JSON and figure artifact. A separate model-artifact scope accepts closed identity files; the manifest binds each file and exposes its model digest and inference-runtime identity as first-class records. An empty model-artifact list therefore means no model result has entered the paper, rather than that model provenance was omitted. Archived protocol JSON may still be present in the ordinary artifact scope without being admitted as model evidence. The source snapshot is source only: paths under build directories, virtual environments and bytecode caches are excluded, and a text file's digest is taken with CRLF collapsed to LF, so the same tree yields the same snapshot hash on a different machine and on a Windows checkout. Files carrying a NUL byte are hashed verbatim. The manifest is a release-time snapshot rather than a continuously maintained view of the working tree: regenerating it is part of the release procedure, and \texttt{check-provenance.py} recomputes every recorded digest, re-expands both artifact scopes and exits nonzero on any mismatch, so a manifest that has fallen behind its tree is a detectable failure rather than a silent one. Continuous integration runs that check on every push to main and every pull request, so the failure is detectable without anyone remembering to look. What it establishes is a property of the commit the job runs on, which is the tip of the pushed branch and the head of the pull request, and not a property of every commit in the history. The manifest is bound in a commit of its own after the work it describes, so a commit that moved a source file carries a manifest that has not caught up until the binding commit lands; that is how the artifact is produced rather than a defect in it, and the gate is what makes the state a reader fetches or reviews bind its own tree. Three properties of the validator matter for what the check is worth. The writer and the validator share one rule module, so the scope, exclusions, schema, digest convention, validator path, reproduction entry point and model identity fields are validator policy rather than values a manifest may narrow. Both missing and extra records fail, and every exact model record is opened and its identity recomputed; a model identity file whose artifact digest or runtime identity reads as unresolved is refused by both rather than written by one and accepted by the other. \texttt{generated\_at\_head\_dirty} is a claim the manifest makes about itself, so the validator re-derives it and fails a manifest asserting a clean generation against a tree that has uncommitted work. And a manifest that claims a clean generation is held to what that claim means: every recorded digest is compared against the bytes committed at \texttt{generated\_at\_head}, read back out of the repository; a missing commit is a failure, so editing the flag or naming an unavailable commit cannot bypass the check. The writer can record a dirty candidate for inspection, but the validator refuses it because no later check can reconstruct what that uncommitted tree looked like when the manifest was written. A validated manifest therefore always names a clean committed generation. The checked release driver waits until the version bump is committed and clean, regenerates the manifest, commits only that manifest and tags the resulting provenance-only child. Before any registry job starts, the release validator checks that parent relation, every recorded digest and expanded scope, each model identity summary, the snapshot hash and every package version against the exact tagged tree. A published tag must be an ancestor of \texttt{origin/main}; only the private pre-push check admits the prospective child that the driver will push atomically. Validation passes the exact checked commit identifier to every publishing job, so none resolves the mutable tag again. Read that way, the content snapshot rather than a package label identifies the source state the numbers in this paper were produced from.

\paragraph{The design-property checks (\cref{sec:leakfree,sec:determinism,sec:replay,sec:contract,sec:transport-gate,sec:agentic}).}
\begin{verbatim}
cargo test -p sharpearena              # golden hashes, leak-free
                                       # property tests, conformance kit
cargo test -p sharpearena-wasm         # native == wasm parity + golden
wasm-pack test --node crates/sharpearena-wasm
                                       # same goldens, run on wasm32
npm test --prefix npm/sharpearena      # replay + tamper detection, and the
                                       # goldens against the shipped .wasm
python -m pytest crates/sharpearena-py # Python surface, check_env,
                                       # seed-band disjointness, canonical
                                       # parser, model-field scheduler,
                                       # strategy ledger and paper-only arm
cd formal && lake build                # abstract forecast invariants
\end{verbatim}
The \texttt{cargo test} line compiles the WebAssembly crate's JSON kernels for the host, so it checks the shared source rather than the WebAssembly build; the \texttt{wasm-pack} line is the one that executes the \texttt{wasm-bindgen} export layer on \texttt{wasm32}, and the npm line is the one that reads the binary the package publishes. All three assert the same committed golden file. The model-field tests inject deterministic model transports and do not download weights or produce an agent-performance result. The MCP regression cases assert that unknown and duplicate symbols and action/weight contradictions fail without advancing the environment. The paper-arm tests use in-memory transports and fixed endpoints; they do not send a broker order. The transport-gate cases of \cref{sec:transport-gate} include the characterization test that runs a wedged agent through the unguarded engine and asserts a full-length scoreable return series, so the defect the gate closes stays visible in the suite rather than only in the changelog. Companion-container evidence belongs to SharpeBench and is outside the commands above (\cref{sec:limitations}).

The current golden tests compare the literal canonical JSON fixtures before computing the FNV-1a fingerprints. The \texttt{SPEC\_HASH} tests separately bind the tape-defining source set to both wrappers and the committed npm binary. Python tests exercise effective-configuration readback, typed native errors, sealed-salt redaction, unknown-field refusal and plan-path containment. These are current engineering checks: running them does not regenerate or reclassify the historical evidence files.

\paragraph{Prospective forecast protocol and cross-product tutorial (\cref{sec:prospective-protocol}).}
\begin{verbatim}
python examples/forecast-quality/tutorial.py \
  --output-dir /tmp/sharpe-forecast-tutorial \
  --sharpebench-dir ../sharpebench
\end{verbatim}
The deterministic tutorial writes two strict forecast ledgers and a digest manifest, asks the sibling SharpeBench checkout to score their exact common support, and compares the result with the committed fixture. Its eight synthetic questions span two resolution-time blocks and include an effective revision, a late attempt that cannot replace it, a pre-open rejection, and blind and consensus-visible information exposures. It is a conformance example, not an empirical model run. The separate prospective runner has prepare, forecast, seal and resolve phases, but no invocation of it contributes a result to this paper.

\paragraph{Rank-eligibility existence witness (\cref{sec:witness}).}
\begin{verbatim}
python paper/src/make-witness.py
  -> paper/evidence/witness.json, paper/figures/witness.pdf
\end{verbatim}
The command replays each seed one bar ahead to recover the true next-bar return (asserting that the canonical tape is policy-invariant), mixes it with a standardized noise path reused at every strength within that path (common random numbers), scores \texttt{sign\_follow} and \texttt{deadband\_hold} through \texttt{score\_run} on every seed and on the pooled series, and first checks eligibility is monotone over the 13-point coarse grid. It bisects only a monotone first crossing, to a resolution of $0.005$ in $s$, on the gap-band witness subset and the F1 table band. The whole procedure is repeated under five independent noise paths per cell, with noise-seed uniqueness asserted in the producer; the first path is serialized as the primary witness and all five are serialized under \texttt{noise\_replicates}, which is what \cref{tab:witness} summarizes. The JSON records every strength's per-seed PSR, pooled DSR, bootstrap $p$-value, eligibility flag, monotonicity check and every bracketed crossing.

\paragraph{Sealed evaluation seeds (\cref{sec:sealed-seeds}).}
\begin{verbatim}
python paper/src/make-sealed-seeds.py
  -> paper/evidence/sealed-seeds.json
\end{verbatim}
The command derives 16 named slots publicly (the eight committed offsets plus eight drawn from the same $2^{16}$ band) and sealed (the same slots under a 32-byte salt from the operating system, committed by SHA-256 before the run), re-runs the predictability probe's band-scan adversary unchanged against both, then reveals the salt and replays the sealed scenarios against the recomputed seeds. The JSON records the commitment, the revealed salt, the table-build time and every per-trial recovery and replay record.

\paragraph{Throughput and compute cost (\cref{sec:protocol-compute}).}
\begin{verbatim}
python paper/src/make-throughput.py
  -> paper/evidence/throughput.json
\end{verbatim}
The command times the Python surface directly (scenario generation, Gymnasium-adapter
stepping, and one full six-policy evaluation over the canonical held-out band on all
three tiers), then shells out to the native and WebAssembly benchmarks and parses their
output, so all three rows of \cref{tab:throughput} come from one invocation. The two
sub-benchmarks also run standalone:
\begin{verbatim}
cargo run --release -p sharpearena --example bench-steps
node npm/sharpearena/bench/throughput.js
\end{verbatim}
Every rate is the median of three repeats of 500 episodes on a $4\times120$ panel, after a
warm-up invocation that is discarded; the evidence JSON records every individual repeat
and the host's platform string, so a reader can see the spread rather than only the
median. Throughput is hardware-dependent and is the one quantity in this paper that a
replicator should expect to differ.

\paragraph{Dispersion layers.} The F2, F3, F5 and F6 scripts serialize the per-episode or per-seed vectors behind every reported interval into their evidence JSONs (\texttt{per\_episode\_regret}, \texttt{per\_seed\_returns} with \texttt{band\_dsr\_ci} and \texttt{transfer\_gap\_ci}, \texttt{dispersion}, and \texttt{per\_episode\_markout\_per\_unit} with \texttt{gap\_stats} respectively), each with its CI convention recorded in the file, so every interval in \cref{sec:validation,sec:findings} is recomputable from the committed evidence.

\paragraph{Regenerating every figure from the committed evidence.}
\begin{verbatim}
python paper/src/make-figures.py
\end{verbatim}
Each \texttt{make-f*} script produces its own figure at run time; \texttt{make-figures.py} re-renders all figures from the JSON already in \texttt{paper/evidence/} without re-running any experiment, so a reader can check that no figure contains a number the evidence does not.
